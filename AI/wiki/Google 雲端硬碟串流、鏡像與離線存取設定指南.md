# Google 雲端硬碟串流、鏡像與離線存取設定指南

整理 Google 雲端硬碟電腦版（Drive for desktop）三種存放方式的運作原理，以 2026-11-18～20 公司筆電 ADM-189 反覆卡死的調查結果為例，建議公司與家裡兩台電腦的設定方式。調查過程記錄在 [[WorkLog]]（2026-11-20「筆電 ADM-189 卡死詳查」）。

**一句話重點**：離線存取只省下載，躲不過虛擬磁碟的讀取瓶頸

## 一、三種方式的觀念

### 1. 串流模式（Stream files）

- Google Drive 建立一個**虛擬磁碟**（本機為 `G:`），用 Dokan 檔案系統驅動程式掛載。`G:/我的雲端硬碟/` 並不是真的硬碟資料夾。
- 檔案平常只在雲端，本機只有檔名、大小等資訊。開啟檔案時才即時下載，並放進本機快取（`%LOCALAPPDATA%\Google\DriveFS\<帳號ID>`）。
- 快取空間不足或久未使用時，Google Drive 會自動清掉本機內容。
- **所有讀寫都要經過 Google Drive 程式處理**：存檔時先寫入快取，再由背景上傳；讀檔時由它從快取或雲端取出內容回傳。

### 2. 離線存取（Available offline，串流模式下的選項）

- 對串流模式中的某個資料夾或檔案按右鍵 →「離線存取」→「可離線使用」。
- 意思是「這些檔案的內容永遠留在本機快取，不要清掉」：會先下載完整內容，雲端有更新時也主動下載。
- **路徑不變，仍然在虛擬磁碟 `G:` 上**，讀寫一樣要經過 Google Drive 程式，上傳和下載也一樣自動進行。
- 設定紀錄在 DriveFS 的 `metadata_sqlite_db`：`item_properties` 表中 `key='explicitly-pinned-folder'` 是明確設定的資料夾，各檔案的 `pinned`、`offlineStatus` 是離線狀態。

### 3. 鏡像模式（Mirror files，雙向同步）

- 「我的雲端硬碟」的所有檔案都**真正存在本機的一般 NTFS 資料夾**，例如 `C:/Users/ch26788/我的雲端硬碟/`。
- 程式讀寫的是真實檔案，不經過虛擬磁碟。Google Drive 在背景比對差異，雙向上傳或下載。
- 佔用本機空間等於整個「我的雲端硬碟」的大小，路徑也和串流模式不同。

### 三者比較

| 項目                | 串流           | 串流＋離線存取          | 鏡像      |
| ----------------- | ------------ | ---------------- | ------- |
| 路徑                | `G:/我的雲端硬碟/` | `G:/我的雲端硬碟/`（不變） | 自訂本機資料夾 |
| 檔案內容在本機           | 只有用過的，可能被清掉  | 指定資料夾永遠在         | 全部      |
| 讀寫經過虛擬磁碟          | 是            | **是**            | 否       |
| 增修刪自動上傳           | 是            | 是                | 是       |
| 別台改的自動下載          | 開檔時才下載       | 主動下載             | 主動下載    |
| 沒網路可用             | 只有快取到的檔      | 指定資料夾可用          | 全部可用    |
| 大量同時讀取（全文搜尋、防毒掃描） | 容易卡死         | **仍容易卡死**        | 正常      |
| 本機空間              | 最省           | 中                | 最多      |

## 二、從這次卡死學到的事

| 觀察 | 說明 |
|------|------|
| 現象 | 整台凍結、只能長按電源鍵；Kernel-Power 41 的 BugcheckCode=0，不是藍屏 |
| 直接證據 | 9 次卡死當下，`drive_fs_*.txt` 都有大量 `LogSlowOperation`（單筆讀取卡 1～5 分鐘），回應執行緒約 15 個全部忙碌；沒卡死的日子為 0 |
| 觸發點 | AI Agent 對 `G:/我的雲端硬碟/Obsidian` 根目錄做全文搜尋（4 次），以及大量刪檔進 `G:\$RECYCLE.BIN`（2 次） |
| 加重因素 | CrowdStrike Falcon 與 Trend Micro Apex One 兩套防毒並存，每次開檔都會再讀一次 |
| 關鍵誤解 | Obsidian 資料夾**本來就設了離線存取**，檔案全在本機，照樣卡死。瓶頸在虛擬磁碟同時處理大量讀取，不在下載 |

> [!WARNING]
> [[Git GUI 與 GitHub 雙向同步實務]] 建議「把專案放在 G: 槽統一跨電腦路徑」。但串流模式的 `G:` 是虛擬磁碟，大量讀取時有卡死風險。鏡像模式只要兩台選用相同的資料夾路徑（例如兩台使用者帳號相同，都用 `C:/Users/<帳號>/我的雲端硬碟/`；帳號不同時可都選 `D:/我的雲端硬碟/` 這類固定路徑），也能達到路徑統一。

## 三、建議設定

### 家裡筆電（`weng`）：維持鏡像模式

- 已經是鏡像模式，檔案都在本機，全文搜尋、git、防毒掃描都不會卡住虛擬磁碟，**不用改**。
- 換電腦前先看系統匣的 Google Drive 圖示，確認已同步完成，避免兩邊同時修改同一個檔案。

### 公司筆電（ADM-189）：分兩階段

**第一階段（已完成，先觀察）：維持串流＋Obsidian 離線存取，靠使用習慣避開**

1. 全域規範開工流程改為直接讀 `WorkLog.md`，並禁止對 `G:` 雲端硬碟或保管庫根目錄遞迴搜尋（chezmoi commit `781672d`，Claude、Codex、Antigravity 三份都改了）。
2. 大量刪除或搬移檔案時分批進行，或用 git 操作；完成後清空 `G:` 資源回收筒。
3. 請資訊單位評估把 `GoogleDriveFS.exe`、`G:\` 加入兩套防毒的掃描排除。

**第二階段（若仍卡死）：改為鏡像模式，這是技術上最好的方式**

改鏡像的理由：

- 「我的雲端硬碟」約 11,385 個檔案、2.5 GB，公司 C 槽還有約 650 GB，空間不是問題。
- Obsidian 保管庫本身是 git repo（約 1,200 個檔案，`.git` 約 500 個）。git 會頻繁掃描大量小檔，在真實 NTFS 上又快又穩，不會塞住虛擬磁碟。
- 兩台都是鏡像，若再選用相同路徑，AI Agent 的規範可以不再分電腦寫兩套（要先確認家裡那台的使用者目錄名稱）。

改鏡像的步驟與注意事項：

1. 先處理舊的孤立複本：公司這台的 `C:/Users/ch26788/我的雲端硬碟/` 是以前雙向同步模式遺留的，規範寫明不可讀寫。改鏡像前要先確認裡面沒有需要的檔案，再改名或刪除，避免 Google Drive 把舊檔當成新檔上傳。
2. Google 雲端硬碟偏好設定 →「我的雲端硬碟」→ 改為「鏡像檔案」，資料夾選 `C:/Users/ch26788/我的雲端硬碟/`，等第一次同步完成。
3. Obsidian 重新開啟新路徑的保管庫；`git status` 確認正常。
4. 修改 chezmoi 規範：把開工流程的「`weng` 例外」改成兩台共用的鏡像路徑。
5. Claude Code 的專案記憶是依路徑存放的（目前在 `~/.claude/projects/G---------Obsidian/memory/`），換路徑後要把記憶檔複製到新路徑對應的資料夾。

## 四、我可以怎麼用

- **在 `G:` 上需要搜尋時**：先讀已知檔案（如 `WorkLog.md`、`AI/wiki/index.md`）；真的要搜就限縮到小的子資料夾，例如 `AI/wiki`，並只比對 `*.md`。
- **再發生卡死時**：對照 `%LOCALAPPDATA%\Google\DriveFS\Logs\drive_fs_*.txt` 中 `LogSlowOperation` 開始的時間，與 Claude、Codex 對話紀錄裡當時的工具呼叫，就能找到觸發點。
- **判斷某資料夾是否已設離線**：檔案總管圖示為綠色實心勾勾；或查 DriveFS `metadata_sqlite_db` 的 `explicitly-pinned-folder`。
- **兩台輪流用時**：一台同步完成，另一台再開 Obsidian 或執行 git。git 出現內容沒變的 `M` 時，`git add` 即可清除。
