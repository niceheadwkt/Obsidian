# 本地 AI 硬體分級與 Ollama 設定五大坑

AI懶人報 Podcast EP460（YouTube，2026-11-04，約 16 分鐘）。這集依記憶體大小，從 16 GB 講到 128 GB：每一級能跑哪些模型、速度大概多少、適合做什麼。也講了 MoE、執行軟體怎麼選、實際做成功與會讓人失望的用法，以及新手常踩的五個坑。片中的速度（tok/s）都是社群實測，不是節目自己量的，只能當作大概參考。

**一句話重點**：本地 AI 常是 context 設太短，不是模型太笨

## 一、開場：為什麼接 agent 一直失敗

- Ollama 官方文件：顯示記憶體 **< 24 GB 的機器，預設 context 只有 4k token**（24～48 GB 是 32k，≥ 48 GB 是 256k）。
- OpenClaw 官方建議，接本地模型時 context **至少要 64k**，和 4k 差了 16 倍。
- agent 工具在你輸入之前，就會先塞進一大段系統說明。社群實測只打一聲「嗨」，就用掉大約 5,000 token，所以 4k 一開始就爆了。

## 二、一條規則：放不放得下

- **4-bit 量化模型大約要「參數量 × 0.6 GB」**：9B ≈ 5.7 GB、27B ≈ 17.6 GB、35B ≈ 22.4 GB（和 Hugging Face 上的實際檔案大小相符）。
- 模型檔放得下還不夠，**context 也要佔記憶體**，要另外留空間。
- **Mac 陷阱**：macOS 預設大約只讓 GPU 使用 3/4 的統一記憶體，16 GB 只剩大約 12 GB、32 GB 大約 24 GB。MLX 有指令可以調高，但重開機後會恢復。

## 三、16 GB 到 128 GB 的分級

速度體感：每秒 < 5 token 幾乎不能用；10 左右約等於讀字速度；20～30 很順；60 以上接近雲端。

| 記憶體 | 能跑的模型 | 速度（社群實測） | 適合做什麼 |
|---|---|---|---|
| 8–16 GB | Gemma 4 E4B（約 5 GB）、Qwen3.5 9B（約 5.7 GB）；gpt-oss-20b（約 12 GB，Mac 上很緊） | 小模型很快 | 改寫、翻譯、摘要、整理成表格；當 agent 容易出錯 |
| 24–32 GB（甜蜜點） | Qwen3.8 27B、Gemma 4 26B、Qwen3.6 35B | 32 GB M6 Mac mini：Qwen 27B 約 8–9 tok/s；Gemma 4 26B 約 33 tok/s | 私人文件問答、批次分類、範圍清楚的 coding agent 小任務。24 GB 偏緊，32 GB 較穩 |
| 64 GB | 最強的**還是 Qwen 27B**（下一級最小也要約 70 GB） | — | 換 8-bit（約 29 GB）提升品質；開長 context（Ollama ≥ 48 GB 預設 256k） |
| 128 GB | gpt-oss-120b（約 63 GB）、Qwen3.8 Flash Next（125B） | M5 Max：60–70 tok/s | 大約是一年前頂級雲端模型的水準；macOS 可用大約 96–107 GB |
| 256 GB 以上 | 更大的模型 | — | 每升一級聰明程度只多一點點，除非資料完全不能外流或要多人共用，否則不划算 |

## 四、為什麼有的大模型反而快：MoE

- 生成每個 token 都要把參數從記憶體讀一遍，速度受**記憶體頻寬**限制。
- 稠密模型每次都動用全部參數；**MoE（專家混合）** 每次只叫出少數專家，例如 Qwen3.6 35B-A3B 每次只用大約 3B 參數。
- 實測同一台 M4 Pro：稠密 27B 是 14.7 tok/s，MoE 35B 是 78.8 tok/s，快了五倍。
- **常見誤解**：MoE 只是比較快，**不會比較省記憶體**，所有專家都要載入。口訣是「放不放得下看全部，速度看每次叫出來的那幾個」。
- 社群回報：長時間的 agent 任務，稠密模型比較穩，MoE 有時會失手。

## 五、執行軟體怎麼選

| 軟體 | 定位 |
|---|---|
| LM Studio | 有完整圖形介面，像模型的 App Store，會提示放不放得下；Mac 上選 **MLX 格式** 通常比較快 |
| Ollama | 主要在背景跑服務，讓 OpenClaw、Claude Code 這類 agent 工具來接，最方便 |
| llama.cpp | 很多軟體底層用的引擎，功能最多，但要自己下指令 |

- 同一台 32 GB M6 Mac mini、同一顆 Qwen 27B，只換軟體和檔案格式，就從大約 8 tok/s 變成大約 21 tok/s。**覺得慢時，先換軟體、更新版本、確認格式，不要急著換電腦**。

## 六、做得好的與做不好的

**有人做成功的例子**：
1. 私人文件問答（合約、病歷、財務資料），斷網也能用。
2. 批次重複工作：40 張範例發票讀成試算表，全部正確。
3. 32 GB Mac mini + Gemma 4 26B，讓本地 coding agent 寫程式分類銀行交易並做儀表板，資料完全不離開電腦。
4. 用 6 GB 的看圖模型整夜幫幾千支影片片段寫說明（跑了 16 小時以上）。
5. **雲端大模型規劃、本地小模型執行**：GitHub Copilot 依任務難度分派雲端或本地模型；Perplexity 在 Mac 上讓本地模型處理私密檔案。

**會讓人失望的情況**：
1. 在大型專案裡當 coding agent：**讀 prompt 的速度**太慢，Mac 讀長 prompt 特別慢，跑了 3 分鐘還寫不出程式。
2. 拿 9B 小模型當 agent 做儀表板，做出來全是錯的；換雲端模型一次就成功。
3. 壓到 4-bit 以下（3-bit、2-bit）時，**最先壞掉的是工具呼叫**。要做 agent，至少留在 4-bit。

## 七、新手五個坑

1. **context 太短**：Ollama 在 < 24 GB 的機器上預設 4k，接 agent 要拉到 64k 以上（會多吃記憶體）。
2. **chat template 遺失**：有些重新打包的版本沒帶到原本的對話格式，軟體改用通用格式，模型就會明顯變笨。請下載官方或口碑好的版本。
3. **KV cache 被壓縮**：硬體評測團隊用 6 個較難的工具呼叫測試，KV cache 壓成 8-bit 後有 5 個格式壞掉（題目是刻意挑的難題，不代表平常的錯誤率）。做 agent 時不要動這個設定。
4. **只看放不放得下**：有人在 16 GB 顯示卡硬塞 27B，記憶體用到 96%，電腦當機。還要考慮 context 空間和讀寫速度。
5. **以為本地一定安全**：SentinelOne 和 Censys 發現有 **175,108 台 Ollama 伺服器直接對外開放、沒有密碼**，將近一半還開了工具呼叫。重點不是在哪裡跑，而是**它碰得到什麼**。

**一個下午就能做完的安全清單**：
- Ollama 保持只聽本機（預設值），要從外面連回來就用 Tailscale 這類私人網路。
- Ollama、LM Studio 保持最新版（都修過好幾次安全漏洞）。
- 會給工具權限的模型，只用官方或知名來源的檔案。
- agent 的工作資料夾不放密碼、金鑰。
- LM Studio 開本地伺服器時，要打開驗證選項。

## 八、什麼時候該升級，與七句照做

- 16 GB 每天都想跑 agent 或 27B 模型 → 升 32 GB 有感；32 GB 常讀長文件、跑長 agent 任務 → 64 GB 才有意義；想跑 100B 以上 → 128 GB。其他情況先把軟體和設定調好。
- 七句照做：①接 agent 先把 context 拉到 64k 以上；②4-bit 大約是參數量 × 0.6 GB，再加 context 空間；③Mac 先照 3/4 記憶體算；④16 GB 跑小模型、32 GB 跑 27B、64 GB 開長 context、128 GB 換大模型；⑤想要快，先試 MoE，再換軟體；⑥難的交給雲端，私密和重複的留在本地；⑦Ollama 只聽本機，agent 資料夾不放密碼。

## 我可以怎麼用

- **評估公司本地 AI 主機時的快速估算**：用「參數量 × 0.6 GB + context 空間」和上面的分級表，先判斷要 32 GB 還是 128 GB 等級，避免只看「放得下」。
- **本地 agent 表現很差時的檢查順序**：先查 Ollama 的 context（預設 4k）→ chat template → KV cache 有沒有被壓縮 → 量化是否低於 4-bit，最後才懷疑模型。
- **ERP 資料的雲地分工**：規劃和難題交給雲端 Claude；含機密的 ERP 資料批次分類、發票辨識、報表摘要這類重複工作，可以評估放在本地模型跑，對應 [[主權 AI 與 token 帳單三層陷阱]] 的成本考量。
- **資安自檢**：如果公司或自己的電腦有裝 Ollama，確認沒有綁到 `0.0.0.0` 對外開放，也確認 agent 的工作目錄裡沒有 token 或密碼檔。
- **大型專案不交給本地 coding agent**：ERP 程式庫很大，讀 prompt 會太慢；本地模型只適合範圍清楚的小任務。
