# Claude 系統優化與 Token 節省指南

**Claude 系統優化與 Token 節省指南** 旨在解決開發者與高頻用戶常面臨的「Tokens 消耗過快」、「頻繁達到用量上限（Usage Limit）」等成本與效率問題。本篇整理了底層 Token 暴漲原因、官方針對 Claude Code 的節流建議、模型定價與選用策略，以及 `CLAUDE.md` 的優化準則。

---

## 1. Token 暴漲的底層原因與優化原則

### 🔍 為什麼 Token 消耗會呈指數型增長？
在大模型的運作機制中，**每次對話並非獨立發生**。為了維持對話連貫性，每次您送出新訊息時，Claude 都會將「`先前的對話歷史` + `載入的上下文文件` + `您的新 Prompt`」打包，作為一個巨大的 Input 重新傳送至雲端進行推理。
因此，若您在同一個 Session（對話）中丟入大檔案並進行了 20 次對話，該大檔案會被重複計費並讀取 20 次，導致 Tokens 瞬間燒光。

### 🛠️ 4 個常見用量超限情境與縮減技巧

1.  **情境一：對話累積過長**
    *   **技巧**：一旦確認某個代碼 Bug 已修復或特定大綱已定稿，請立即開新對話（New Session），不要在同一個對話中無限延伸。
2.  **情境二：直接上傳超大 PDF 文獻**
    *   **技巧**：避免將數百頁的書籍或論文直接整本丟給 AI。先用工具將 PDF 切割成關鍵章節，或僅複製出與當前任務直接相關的文字段落。**光是將 PDF 進行結構化分段處理，Token 消耗量就可相差達 22 倍**。
3.  **情境三：反覆重寫整個代碼檔案**
    *   **技巧**：在修改代碼時，不要讓 AI 盲目地將整個檔案重新輸出。在 Prompt 中明確要求：「請僅輸出需要修改的代碼區間（Diff 格式）或特定 Function 即可」。
4.  **情境四：冗餘的 System Prompt 與背景資訊**
    *   **技巧**：遵循「少即是多」原則，剔除 Prompt 中那些客套、重複、或無關痛癢的背景描述，將指令聚焦於核心任務。

## 2. Claude Code (終端機 CLI) 官方 4 條節流建議

當您在本地使用 [[Claude（Anthropic）|Claude Code]] CLI 工具時，其高頻的檔案掃描與指令執行容易在不知不覺中消耗大量額度。官方給出以下 4 條防禦建議：

1.  **限制終端機輸出長度**：避免在對話中執行如 `git log`、`npm test` 等會產生上千行文字的命令。建議使用 `git log -n 5` 或過濾特定錯誤訊息，防止大量終端文字被打包成上下文發送。
2.  **配置排除清單 (.gitignore)**：確保將 `node_modules/`、`build/`、`dist/` 以及像 `.obsidian/workspace.json`（參見 [[Git GUI 與 GitHub 雙向同步實務]]）等隨時變動的環境暫存檔寫入排除名單，防止 Claude Code 在掃描專案目錄時將其完整讀取。
3.  **適時使用 `/clear` 命令**：當前任務（如完成一個 Feature 開發）結束後，於終端機輸入 `/clear` 清空當前對話記憶，以乾淨的上下文開始下一個 Bug 的修復。
4.  **精確指引檔案範圍**：若專案很大，在要求 Claude Code 編輯或讀取時，指明具體檔案路徑與行數（如：`請幫我修改 src/utils.py 的第 45 行至 60 行`），避免 AI 掃描不相關的模組。

## 3. 模型選用策略：Opus vs. Sonnet vs. Haiku

選擇合適的模型是控制成本的核心。若盲目使用最強的模型處理簡單任務，**可能會多花費高達 5 倍的 Token 成本**：

| 模型名稱 | 推理能力 | 速度 | 價格比 | 適合場景 |
| :--- | :--- | :--- | :---: | :--- |
| **Claude 3.5 Sonnet** | 極強（代碼能力首選） | 快 | 中 | **主力開發模型**。適合程式撰寫、複雜語意推理、系統整合。 |
| **Claude 3.7/4.0 Opus** | 頂級推理（邏輯與規劃） | 慢 | 高 (約 Sonnet 2.5倍) | **技術藍圖設計**。適合前期架構規劃、高難度數學/物理推導，不建議用於日常瑣碎問答。 |
| **Claude 3.5 Haiku** | 中等（日常對話與快速處理） | 極快 | 低 (約 Sonnet 1/5) | **低成本極速首選**。適合代碼語法糾錯、大批次文字翻譯、簡單分類與過濾任務。 |

## 4. CLAUDE.md 12 條行為規則：將錯誤率從 41% 降至 3%

在 [[Claude 專案管理一桌三櫃工作流|一桌三櫃工作流]] 中，`CLAUDE.md` 是引導 Claude Code 的本地專案指導書。本節整理《數位時代》2026-05-18 報導的 12 條規則。這 12 條是要求 AI 寫程式時**怎麼做**的行為規則，不是規定 `CLAUDE.md` 要寫哪些內容。

### 4.1 前提：這 12 條是在什麼條件下有效

- **時間與模型**：2026 年 5 月，Opus 4.x 時代。當時模型會提早停下，需要人不斷提醒。
- **演進來源**：2026 年 1 月 Karpathy 抱怨 AI 寫程式的三種錯誤（不問就自行假設、過度設計、順手改動不相關的程式碼）→ Forrest Chang 整理成 4 條，GitHub 逾 12 萬顆星 → Mnimiy 擴充成 12 條。
- **前 4 條的定位**：解決單次對話中的寫程式錯誤。
- **後 8 條的理由**：補多步驟 Agent 任務的漏洞，包括長任務迷失方向、新舊寫法被平均混合、為亮綠燈而寫的假測試、原型開發被「簡單至上」綁手綁腳。
- **測試條件**：6 週、30 個程式碼庫、50 個任務。錯誤率指「需要開發者手動修正的比例」。
- **結果**：無規則 41% → 4 條 11% → 12 條 3%。遵循度由 78% 微降至 76%，代表仍約有四分之一的情況 AI 不照規則做。
- **適用範圍**：結構明確的重構任務效果顯著，高度創意或探索性的開發效果有限。
- **附帶發現**：寫抽象規則勝過寫範例（3 個範例約等於 10 條規則的 token，且容易過度擬合）；「請仔細思考」「你是資深工程師」這類情緒喊話與角色扮演是雜訊；不要寫綁定特定工具的死指令（例如「永遠使用 ESLint」），改寫成「配合專案強制執行的風格」。

### 4.2 12 條規則

| # | 規則 | 說明 |
| :---: | --- | --- |
| 1 | 寫程式前先思考（Think Before Coding） | 說出假設；不確定就問，不要猜；有更簡單的解法要提出；卡住就停下來說哪裡不清楚 |
| 2 | 簡單至上（Simplicity First） | 用最少程式碼解決當下問題，不做推測性功能，不為只用一次的程式碼建抽象層 |
| 3 | 手術式修改（Surgical Changes） | 只改必要範圍，不「順手改善」周邊程式碼、註解、排版；只清理自己這次造成的殘留 |
| 4 | 目標導向執行（Goal-Driven Execution） | 定義成功標準，循環到驗證通過為止 |
| 5 | 只讓模型做需要判斷的事（Use the model only for judgment calls） | 分類、摘要、草擬交給模型；路由、重試、狀態碼判斷等確定性邏輯交給程式碼 |
| 6 | Token 預算不是參考值（Token budgets are not advisory） | 每任務 4,000、每 session 30,000 tokens；接近上限就總結後重開，不要硬撐 |
| 7 | 衝突攤開講，不要平均（Surface conflicts, don't average them） | 兩種既有寫法矛盾時選一種（優先較新或測試較完整的），說明理由，標記另一種待清理 |
| 8 | 寫之前先讀（Read before you write） | 先讀檔案的 exports、直接呼叫者與共用工具；「看起來無關」是最危險的一句話 |
| 9 | 測試驗證意圖，不只驗證行為（Tests verify intent） | 測試要說明行為為何重要；業務邏輯改了測試卻仍通過，代表測試無效 |
| 10 | 每個重要步驟後設檢查點（Checkpoint after every significant step） | 回報已完成、已驗證、剩餘事項；說不出目前狀態就停下來重新釐清 |
| 11 | 遵從既有慣例，即使不同意（Match the codebase's conventions） | 專案內一致性優先於個人偏好；認為慣例有害就提出，不要私自另起一套 |
| 12 | 錯誤要大聲說（Fail loud） | 有任何略過或無法確認的地方，不准回報「完成」或「測試通過」 |

### 4.3 用 Opus 5.5 新原則重新檢視

> [!NOTE]
> 下表是 Claude Code 依 [[Claude Code 少叮嚀多設限：Opus 5.5 時代最佳實踐]] 的原則（CLAUDE.md 只留程式碼看不出來的事、安全靠 deny 規則與環境、品質靠驗證點）推出的判斷，Lydia Hallie 的演講並未逐條評論這 12 條。

| # | 依新原則 | 理由 |
| :---: | --- | --- |
| 1 | 刪 | 新模型本來就會這樣做；「卡住就停下來問」也和長時間自主執行相衝突 |
| 2 | 刪 | 通用叮嚀，新模型的預設行為 |
| 3 | 刪 | 同上 |
| 4 | 搬家 → 任務指令＋hooks | 正是第一層驗證點，但應寫在每次任務的「完成長什麼樣」與 hooks，不放 CLAUDE.md |
| 5 | 留，但不放 CLAUDE.md | 屬於設計 AI 應用的架構原則，不是 Claude Code 行為規則 |
| 6 | 刪（已過時） | 與現在單一 session 跑數小時、自動壓縮脈絡的做法矛盾 |
| 7 | 改寫成具體事實 | 通用版刪；專案若真有新舊兩套寫法，寫明以哪套為準——這正是程式碼看不出來的事 |
| 8 | 刪 | 新模型的預設行為 |
| 9 | 搬家 → CI＋另一個 Claude 審查 | 品質改由獨立驗證點把關 |
| 10 | 搬家 → hooks 與驗證點 | 人不再逐步盯，改看驗證點結果 |
| 11 | 改寫成具體事實 | 通用版刪；只留模型看不出來的慣例，例如 ERP 檔案必須 Big5 |
| 12 | 搬家 → Stop hook 回 exit code 2 | 由機制強制，比文字叮嚀可靠 |

結果：刪 5 條（1、2、3、6、8）、搬家 4 條（4、9、10、12）、改寫成專案具體事實 2 條（7、11）、另放 1 條（5）。

> [!NOTE] 已更正（2026-11-25 結案）
> 根據本節的 12 條規則實測（2026-05，Opus 4.x），規則由 4 條擴充到 12 條仍有效，遵循度幾乎不降；但 [[Claude Code 少叮嚀多設限：Opus 5.5 時代最佳實踐]] 引述 Anthropic 2026-11 演講，主張 Opus 5.5 時代強硬的通用叮嚀反而會拖累模型，CLAUDE.md 只留程式碼看不出來的事。
> **結論（依模型世代）**：Opus 5.5 以後以「少叮嚀、多設限」為原則；12 條實測保留為 Opus 4.x 的歷史紀錄。三師爸的全域規範 2026-11-23 決定暫不瘦身，因為內容多為環境事實（路徑、編碼、工具）與禁止事項，本來就屬於該留下的類型。

### 4.4 規則自我審查：一段提示＋每週排程

來源：《數位時代》〈CLAUDE.md 規則越加越爛？〉，整理自 X 使用者 @itsolelehmann 的貼文。作者刪掉一半 Claude Cowork 設定後，輸出品質反而提升。原因是規則只加不刪，會累積重複、衝突（例如「要簡潔」vs「一定要解釋所有術語」）與 AI 本來就會做的事。

**第一步：把這段自我修正提示丟給 Claude**（Claude Cowork 或 Claude Code 可直接讀取所有設定，不必手動貼內容）

```text
在回答之前，請先完整閱讀我的所有設定。檢查我的 CLAUDE.md、skills 資料夾中的每一個 skill、
context 資料夾中的每一個檔案，以及任何你能找到的其他指令檔案。
接著逐一審查你找到的每條規則、指令與偏好設定。針對每一條，告訴我：
1. 這是你不需要被告知就會預設執行的行為嗎？
2. 這條規則與我設定中其他地方的規則有衝突或矛盾嗎？
3. 這條規則與另一條規則或另一個檔案中的內容重複了嗎？
4. 這條規則看起來像是為了修正某一次特定的糟糕輸出而加入的，而不是為了整體改善輸出品質？
5. 這條規則模糊到每次你的解讀都可能不同嗎？（例如：「更自然一點」或「用好的語氣」）
最後請提供：
- 所有你建議刪除的條目清單，每條附上一行刪除理由
- 各檔案之間發現的衝突清單
- 去除冗餘後的精簡版 CLAUDE.md
```

**第二步：收到報告後這樣刪**（不要全盤接受，也不要一條一條慢慢刪）

1. 讀每一條被標記的項目和理由；對某條有異議就保留。
2. 剩下的一次全部刪除，才感受得到整體差異。
3. 用最常跑的 3 種任務測試清理後的設定。
4. 輸出品質維持或變好 → 刪掉的規則確認無效。
5. 某個任務的輸出變差 → 只把那一條加回去。

**第三步：設定每週一自動審查**（在 Claude Cowork 對話視窗輸入）

```text
建立一個名為「setup-audit」的每週排程任務，於每週一早上 9 點執行。
任務內容：完整讀取我的所有設定（CLAUDE.md、所有 skills、所有 context 檔案，以及一切相關檔案），
接著對每一條規則套用以下 5 個篩選條件進行審查：
1. 這是你不需要被告知就會預設執行的行為嗎？
2. 這條規則與我設定中其他地方的規則有衝突或矛盾嗎？
3. 這條規則與另一條規則或另一個檔案中的內容重複了嗎？
4. 這條規則看起來像是為了修正某一次特定的糟糕輸出而加入的，而不是為了整體改善輸出品質？
5. 這條規則模糊到每次你的解讀都可能不同嗎？
最後請提供：
- 建議刪除的條目清單，每條附上一行理由
- 各檔案之間發現的衝突清單
- 規則總數中通過審查與被標記的數量摘要
不要修改任何檔案，僅輸出報告。
```

**使用前提**

- 週期排程要用 Claude Cowork 或 Claude Code；只用 Claude.ai 網頁版時，提示詞仍可用，但排程改為手動執行。
- 不要把報告當聖旨：Claude 可能標記你確實需要的個人工作流程設定，最後由你決定刪不刪。
- 效果取決於設定多臃腫：本來就精簡的話，可能只找到 2、3 條可刪，不代表方法無效。
