門禁與承攬商安全衛生管理系統
新進人員教育訓練

本教材帶你從業務面、系統架構、資料表、刷卡硬體到維運排障，完整認識 HG 門禁系統與 QG 承攬商入口。讀完後，你應該能獨立回答使用者的常見問題，並知道遇到異常時從哪裡查起。

適用對象：資訊課新進同仁、HG 系統接手維護人員 建議時數：三天（含實機操作） 整理日期：2026-10-02

01課程導覽

先掌握學習目標與這套系統「為什麼存在」。

為什麼要有這套系統

承攬商人員進入廠區施工，必須確認身分、證件效期、保險、工安訓練與當日派工。系統在門口刷卡的瞬間，用畫面、聲音、燈號即時告訴警衛「這個人可不可以進廠」。

它影響誰

刷卡資料會提供給「計價系統」與「採購系統」做承攬商計價與扣款，也是勞檢報表、保險勾稽的依據。刷卡資料正確是首要之務。

你要學會的事

1. 說出證件申請到刷卡入廠的完整流程。
2. 看懂申請單狀態碼與主要資料表。
3. 理解刷卡機、門禁主機、ERP、製卡機之間的資料流。
4. 依異常訊息判斷問題落在哪一段。

03業務流程與狀態碼

承攬商人員從「還沒進過廠」到「每天刷卡上工」的完整路徑。

  1. 建立基本資料承攬商在 QG（或同仁在 HG）建立廠商（TBHG101）、人員（TBHG102，含照片）、車輛（TBHG103）資料。人員照片須為 .jpg、檔名為身分證號。
  2. 人力需求申請（B01）依合約或訂購單提報需求人數與工作期間，主管線上核准、退回或擬准。
  3. 工作證申請（B02 長期／B03 臨時／B04 車輛／B05 臨時通行證／B11 承租）建立申請主檔 TBHG201 與明細 TBHG202（人員）或 TBHG203（車輛），送出後進入主管簽核。
  4. 簽核與繳費主管審批後狀態轉為已核准，審核通過自動通知行政處（群組 HGA1GROUP）製證。
  5. 製卡發證行政處以製卡機製卡，出入證資料寫入 TBHG206，狀態為 D01（發證）。
  6. 每日派工（C01）承攬商填寫當日派工名單（TBHG204／205），派工地點必須與刷卡地點一致。
  7. 刷卡入廠門口卡鐘刷卡，門禁主機即時判斷可否入廠，並寫入出入紀錄 TBHG301。臨時人員由警衛在「門哨放行作業」換證放行。
  8. 後續應用刷卡紀錄經排程配對（TBHG402）、保險勾稽，提供計價、採購與各類報表。

08刷卡機與通訊

門口那一刷，背後經過了五個步驟。

  1. 卡鐘送出卡號卡鐘以 TCP 連到控制主機的 SocketServer，入廠用 port 4660、出廠用 port 4661。
  2. 控制主機轉送CommWithServ 以 HTTP 將〔卡鐘 IP、卡號、HG004 代碼〕送到 http://{setup 第一行}/erp/hg/hgjsC05。
  3. 門禁主機判斷hgjsC05 檢查卡片、證件效期、派工、允許入廠時間等，寫入 TBHG301。卡鐘 IP 奇數判定為入廠、偶數為出廠。
  4. 回傳結果回傳陣列：[0] 身分證號、[1] 姓名、[2] 廠商編號、[3] 廠商名稱、[4] 結果、[5] 結果說明、[6] 異常訊息。
  5. 畫面、聲音、燈號控制主機重繪警衛畫面（含照片），播放 OK.wav／ERROR.wav，並透過 Led.java 控制紅綠燈。

門禁程式改版與打包

  1. 原始碼在 erp.war/hg/ipc（Main、SocketServer、CommWithServ、Led、IPCPanel、Sound）。
  2. 將 ipc、net 兩個目錄的 class 編成 jar（燈號控制使用 jamod 函式庫）。
  3. 以 JSmooth 打包成 exe：skeleton 選 console wrapper → application 指定 embedded jar 與 main class → executable 設定圖示與檔名 → compile。
  4. FTP 上傳到控制主機 D:\ftproot，以 VNC 連線重啟程式並實際刷卡測試。
每一廠的 exe 版本不同熱軋、冷軋第二台的紅綠燈是不同 IP，鹿港的 UnitID 特殊，所以各廠 exe 不能互相覆蓋。改版前先確認該廠目前使用的版本。

佇列卡住怎麼辦

同仁反應「刷卡資料沒進來」或「門口刷不過」，常是 ERP 與門禁主機資料不同步。MQ 遇到格式錯誤的資料會一直重試，導致後面資料全部卡住。

  1. 登入 MQ 管理介面找到消化數停住的佇列，點進去查看錯誤資料內容與卡住時間。
  2. 跳過錯誤資料先「停用」佇列 → 重新整理（消化端由 1 變 0）→ 輸入要跳過的筆數，按「跳過」→ 按「啟用」。
  3. 比對兩邊筆數依卡住時間，比對正式機與門禁 DB：tbhg102、tbhg201、tbhg202、tbhg204、tbhg205、tbhg301。
  4. 補齊資料將筆數多的一方資料倒入筆數少的一方，並記錄處理過程。
-- 兩邊各執行一次，比較筆數（日期取卡住前一天）

11異常處理手冊

先分類，再處理。異常分三種：

a刷卡機端

警衛執行了錯誤的 exe、執行檔或參數檔被移動、音效檔被改名、控制主機當機。

處理：VNC 連線檢查 D:\ftproot，執行 Restart_GateSystem.bat。

b刷卡機與正式機之間

網路阻塞、hgjsC05 回傳 HTTP 500、MQ 佇列卡住。

處理：查控制主機 log、檢查門禁主機服務、處理 MQ（第九章）。

c申請資料異常

證件過期、卡號不是最新、沒有派工、派工地點不符、停權。

處理：依刷卡畫面訊息，倒推檢核順序。

由刷卡訊息倒推檢查順序

例：畫面顯示「本日非入廠日期」，對應到「有無派工」，處理順序為：查詢派工 → 確認刷卡時間正常 → 工作證申請確認 → 出入證基本資料維護。

常見問題

承攬商刷卡失敗，需要補登刷卡資料
到（IHGCD）《人員出入廠記錄查詢》點選新增補登。若涉及保險或計價，注意排程順序：補登後要等配對排程跑過，下游系統才抓得到。計價需要的資料，不可只補到「外包投保」那一段。
刷卡後畫面訊息空白、燈號顯示錯誤
1. 等五秒後再刷一次（網路可能暫時阻塞）。
2. 確認卡號是最新的：《人員基本資料》的【人員辦證紀錄】頁籤。
3. 確認資料有沒有進正式機，再依刷卡檢核流程逐項檢查。
4. 查看控制主機 log，若出現 Server returned HTTP response code: 500 for URL: .../hgjsC05，代表門禁主機端程式出錯，需查伺服器。
刷卡正常，但正式機查不到刷卡紀錄
先請對方等五秒重刷。若持續發生，檢查 MQ 第一組（HG002S → HG002SS）是否卡住；並可在 SQL 命令中心直接查 TBHG301。臨時工作證則要確認警衛是否在《臨時工作證門哨放行作業》確實「發證」，以及當日是否有派工。
當日明明有派工，卻顯示無派工資料
確認派工地點與刷卡地點（HG004 代碼）一致，並確認派工資料已透過 MQ 同步到門禁主機（TBHG204／205 兩邊筆數）。
有發卡也有派工，卻出現「查無卡片資料」
確認卡號是最新的；必要時請該廠到製卡機「過卡」。也可以查製卡機資料：SELECT * FROM HGCARDUSER.PERSON WHERE empNo = '卡號'。
某些人刷卡反應特別慢
除了網路因素，常見原因是照片檔案太大。請將照片縮小後重新上傳。
人員照片一直上傳失敗
三個條件缺一不可：真正的 .jpg 格式（只改副檔名不行）、檔名為身分證號、尺寸符合畫面指示。可用小畫家另存為 JPG。
承攬商人員離職或卡片毀損
請各廠授權人員到（IHGBJ）《出入證基本資料維護》修改卡片狀態，或用 hgjjb06 辦理繳回、遺失、毀損、註銷。
卡鐘時間與實際時間不同
刷卡時間以控制主機為準。確認控制主機有與 stdtime.chsteel.com.tw 同步；卡鐘本身時間差太多時，依第八章「卡鐘校時」步驟處理。
工作證申請送錯，要退回「尚未送出」
需同時處理三張表：將 TBHG201 的 status 改回 A01 並清空 nextOp、dwMsg；刪除 TBHG001 中 forKey 為該單號的核准資料；刪除 TBDW11 中對應的待辦訊息。這是正式機資料修改，必須先取得主管同意並留下紀錄。

年度例行作業

每年年底：臨時工作證確認 TBHG206 中 cardType = '03' 的臨時工作證資料，必要時以 HG交接/HG/每年作業/匯資料至tbhg206.csv 匯入。userange 為空白代表任何一廠都可使用。系統以「年」為單位設計，年初第一個上班日刷卡量大，要提前確認長期工作證換證狀況。

12開發與上線須知

這些是前人踩過的坑。

編碼：Big5／CP950

HG、QG 的 .java、.jsp、.sql 多為 Big5 編碼，用 UTF-8 開啟會亂碼，存檔時也會毀損中文。請使用支援 CP950 的編輯方式，修改後檢查編碼。

版本控管：CVS

程式以 CVS 管理（目錄中的 CVS/ 資料夾）。修改前先比對 CVS 最新版本，避免覆蓋他人修改。

門禁主機沒有 DA 上線機制

ERP 正式機走 DAJJU1 上線申請，但門禁主機（hgserver）沒有，修改 hgjsC05 等程式後，要請網管單位（A32）人工把 class 放上去。

若只需替換 jar 中的 class：jar uvf ./bin/hg.jar -C classes /

新增刷卡地點要改很多支程式

除了 HG004 兩邊加代碼、hgjsC05 支援新卡鐘外，以下查詢需把同廠多台刷卡機合併顯示：HGJJC02、HGJJC03A／B／C、HGJJC06、HGJJC07、hgjcMagDR001～003。

案例：工作證明細的「核准」下拉其實沒有作用

在 hgjjb02 長期工作證申請的明細中，畫面有「核准／不核准」下拉（cardOk），但寫入資料庫前，hgjcb02StaffEntity.create()／update() 會呼叫 checkValidDate() 重新判斷並強制覆寫 TBHG202.isOk：

規則內容性質結果
0起日為空（上傳資料）直接跳過前置不檢查
1明細期限超出申請單期限軟性isOk = N
2TBHG102 查無此人硬性丟例外，整筆交易回復
3停權期間（TBHG303）重疊軟性isOk = N
4同一人在其他申請單已有重疊的有效證件軟性isOk = N

軟性檢核的原因只寫在 log，畫面看不到。使用者問「為什麼被判不核准」時，要從這四條規則去查。B02、B11、QG 的 EC 申請與上傳都共用這個 Entity；B03、B04、C01 則各有自己的 checkValidDate()。詳見 erp.war/hg/HGJJB02_cardOk核准判斷分析.md。

正式機資料修改原則查詢可以在 SQL 命令中心進行；任何 UPDATE／DELETE 都要先備份原資料、取得主管同意，並記錄申請單號、修改原因與時間。

自我測驗

QG 與 HG 的關係是什麼？
QG 是承攬商電子商務入口的畫面層，後端透過 zpjcWebServiceUtil 呼叫 HG 的 api（*EC 類別）與 DAO 完成業務處理。
申請單狀態 B01、B02、D01 分別代表什麼？
B01 主管審批中、B02 已核准、D01 發證。
刷卡紀錄存在哪張表？由哪支程式寫入？
TBHG301 人員車輛出入紀錄檔，由門禁主機上的 hgjsC05 寫入，再經 MQ HG002S 同步回 ERP 正式機。
卡鐘 IP 10.125.15.7 是入廠還是出廠？屬於第幾台？
冷軋廠第二台的入廠卡鐘（奇數為入廠；結尾 6～10 為第二台）。
新增一個刷卡地點，ERP 端至少要做哪兩件事？
正式機與門禁主機的簡易代碼 HG004 都要加相同代碼；控制主機 setup.txt 第八行填入該代碼。另需修改 hgjsC05 與相關查詢程式的合併顯示。
MQ 佇列卡住，跳過錯誤資料後還要做什麼？
依卡住時間比對正式機與門禁 DB 的 tbhg102、201、202、204、205、301 筆數，把缺少的資料補齊。
使用者說 hgjjb02 明細明明選了「核准」，存檔後卻變成不核准，為什麼？
Entity 的 checkValidDate() 會重算並覆寫 isOk，畫面選項不影響結果。可能是期限超出申請單、停權期間重疊，或已有其他有效證件。
為什麼修改 hgjsC05 後不能用 DAJJU1 上線？
hgjsC05 在門禁主機上執行，門禁主機沒有 DA 上線機制，需請 A32 人工上線。
