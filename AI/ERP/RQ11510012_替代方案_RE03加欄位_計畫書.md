# RQ11510012 替代方案計畫書：關聯文件編號改存 RE03 新欄位（草稿 v0.1）

- 需求單：RQ11510012（風險評估系統優化）
- 撰寫日：2026-10-12
- 對應文件：[[RQ11510012_風險評估系統優化_規劃設計]]（v0.3）第 3.3.3 節「關聯文件編號寫入 `tbeaWorkDocEX`」
- 性質：**替代方案**。本文件只處理「新版複製的追蹤資料存在哪裡」；R1～R6 其他設計（版次管控、最新B表 SQL、方案 B 核准時移轉 HC、預估評估共用方法等）全部沿用 v0.3，不重寫。

---

## 1. 背景與目的

v0.3 在「不改表結構」的前提下，把新版複製的追蹤資料寫成 `tbeaWorkDocEX` 的「追蹤列」。因為 field7 只有 10 碼，必須用以下權宜做法：

| v0.3 權宜做法 | 原因 |
|---|---|
| WorkDocID＝`CP`＋新 formNo＋flow0＋flow1＋srlNo（4 碼補零） | 防止和高風險文號主鍵撞號 |
| field1 放關聯文件編號（不是 formNo） | field7 放不下 28～31 碼的文號 |
| field5 一定要留空 | 既有查詢用 field5＝versDate 判斷高風險列，留空才不會被誤認 |
| field6 放 RA／HR／HC／RO、field7 放 HC 移轉日 | 欄位語意要靠文件約定 |
| 刪除 B 表列、作業時要連帶刪 CP 追蹤列（B9） | 追蹤列和 RE03 沒有實體關聯 |
| `getWorkDocNumber()` 修正要加 `WorkDocID NOT LIKE 'CP%'` | 追蹤列混在高風險列裡 |

追蹤資料本質上是「B 表每一列的原始依據」，和 RE03 是**一對一**。本方案改在 `db.tbeaRE03` 直接加欄位，讓追蹤資料跟著 B 表走，去掉上述所有約定。

---

## 2. 方案內容

### 2.1 新增欄位

| 欄位 | 型態 | 預設 | 內容 | 對應 v0.3 追蹤列 |
|---|---|---|---|---|
| `refType` | VARCHAR(2) | `''` | 關聯類型：RA／HR／HC／RO；空白＝非新版複製產生 | field6 |
| `refDocNo` | VARCHAR(40) | `''` | 關聯文件編號：HR／HC＝舊高風險文號；RA／RO＝來源評估文號 | field1 |
| `hcTransDate` | VARCHAR(8) | `''` | HC 移轉完成時寫入核准日（yyyymmdd）；空白＝尚未移轉。兼作防止重複移轉的旗標 | field7 |

- 寬度依據：高風險文號 28～31 碼、評估文號 18 碼，40 碼與 `tbeaWorkDocEX.WorkDocID` 同寬。
- 日期沿用 ERP 慣例存 8 碼字串。
- 寫法沿用 `db.tbeaRE03.sql` 既有風格：`NOT NULL WITH DEFAULT ''`，舊資料自動為空白，不會有 null。

### 2.2 DDL

```sql
-- RQ11510012：新版複製追蹤欄位
ALTER TABLE db.tbeaRE03
  ADD COLUMN refType     VARCHAR(2)  NOT NULL WITH DEFAULT ''
  ADD COLUMN refDocNo    VARCHAR(40) NOT NULL WITH DEFAULT ''
  ADD COLUMN hcTransDate VARCHAR(8)  NOT NULL WITH DEFAULT '';
```

- 新欄位會加在資料表最後面（RANK 之後），不影響既有欄位順序。
- 主鍵不變（compId, formNo, flow0Code, flow1Code, srlNo）。
- 權限：既有 `GRANT … TO USER JAVAUSER` 是針對整張資料表，加欄位後不用重新授權（需 DBA 確認，見 Q-B2）。
- 是否加索引：B2 鎖定檢查要「用舊高風險文號反查新 formNo」（見 3.3），會依 `refDocNo` 跨單查詢。先查正式機 RE03 筆數再決定（Q-B4）；需要時再補：
  ```sql
  CREATE INDEX db.ixeaRE03_ref ON db.tbeaRE03 (refType, refDocNo);
  ```

**回退 DDL**（上線失敗、需要還原時）：

```sql
ALTER TABLE db.tbeaRE03 DROP COLUMN hcTransDate DROP COLUMN refDocNo DROP COLUMN refType;
-- DB2 LUW 執行 DROP COLUMN 後資料表會進入 REORG pending，需要再執行：
-- CALL SYSPROC.ADMIN_CMD('REORG TABLE db.tbeaRE03');
```

> 加欄位（ADD COLUMN）在 DB2 LUW 一般不會造成 REORG pending，但刪欄位（DROP COLUMN）會。實際平台與做法請 DBA 確認（Q-B3）。由於回退成本較高，建議回退時**只還原程式、保留欄位**（新欄位有預設值，舊程式補上欄位清單後完全不受影響，見 4.1）。

### 2.3 DAO 定義與產生

| 檔案 | 動作 |
|---|---|
| `ea/dao/eajcRE03.dao` | `#Field` 最後補三列（refType／refDocNo／hcTransDate，String，isKey n） |
| `ea/src/com/chsteel/ea/dao/eajcRE03DAO.java`、`eajcRE03VO.java` | 用 daotool 重新產生（不手寫）；**產生後要把原本手寫的方法（`copyByFormNo()`、`removeByFormNo()` 等第 550 行以後的自訂方法）搬回去**，重新產生前先備份 |
| `ea/dao/sql/db.tbeaRE03.sql` | 保留原 CREATE；另外新增 `db.tbeaRE03_RQ11510012.sql` 存放 2.2 的 ALTER 與回退 DDL，一起提交 CVS 留檔 |

> 注意：重新產生後的 `create()`、prepared INSERT 會帶 19 個欄位，`getInstance(rs)` 會依位置讀 19 欄。**新的 DAO／VO 只能在 ALTER 完成後部署**（見第 5 節上線順序）。

## 5. 上線步驟與順序

因為 4.1 的 INSERT 和 2.3 重新產生的 DAO，**DDL 和程式必須在同一個上線時段**，順序如下：

| 步驟 | 動作 | 環境 |
|---|---|---|
| 1 | 測試機執行 ALTER（2.2） | 測試機 |
| 2 | 改 `.dao`、daotool 重新產生、搬回手寫方法；改 4.1 三處 INSERT；實作第 3 節 | 測試機 |
| 3 | 回歸測試（第 6 節 T-B1～T-B5）＋ v0.3 原有測試（T1～T12，改用 RE03 欄位驗證） | 測試機 |
| 4 | CVS 提交（含 `db.tbeaRE03_RQ11510012.sql`） | — |
| 5 | 依公司程序申請正式機 DDL（Q-B1） | — |
| 6 | DAJJU1 上線申請，上線說明註明「需先執行 DDL」 | — |
| 7 | 上線當天：**先**執行正式機 ALTER → 確認欄位存在 → **再**部署程式 | 正式機 |
| 8 | 上線後驗證：原「複製」、B 表匯入、B 表維護各操作一次 | 正式機 |

**風險窗口**：步驟 7 中 ALTER 完成到程式部署完成之間，舊程式的「複製」和「B 表匯入」會失敗（4.1）。應選在使用者不操作的時段，並且盡量縮短這段時間。

**回退方案**：

| 狀況 | 處理 |
|---|---|
| ALTER 失敗 | 不部署程式，原系統不受影響 |
| 程式部署後有問題 | **不可**直接還原成上線前的舊版程式（舊版 `copyByFormNo`、`doImport` 遇到新欄位會壞）。應還原成「只改 4.1 三處」的過渡版並保留欄位；不得已時才執行回退 DDL |

> 也可以把上線拆成兩次，降低風險：**第一次**只上線 4.1 的三處修正（補欄位清單，對現況沒有影響，可以先上）；**第二次**執行 ALTER＋上線新功能。這樣在 ALTER 前後，舊程式都能正常運作，也不會有風險窗口。**建議採用兩段式上線。**

## 8. 兩方案比較

| 項目 | v0.3（WorkDocEX 追蹤列） | 本方案（RE03 加欄位） |
|---|---|---|
| 改資料表結構 | 不用 | 要（ALTER 3 欄） |
| 動到既有程式 | 不用 | 3 處 INSERT 補欄位清單＋DAO 重新產生 |
| 上線 | 只部署程式 | DDL＋程式，建議兩段式 |
| 資料語意 | 靠約定（CP 前綴、field5 留空、field6／7 意義） | 欄位名稱就是意義 |
| 與 B 表的關聯 | 靠 WorkDocID 字串組合 | 同一列 |
| 刪除、修改 B 表時 | 要連帶處理追蹤列（B9） | 自動跟著走 |
| 對現有 WorkDocEX 查詢的影響 | 要逐一確認不會誤判（`queryWorkDocEX`、HR_LATEST、`exWD()`、取號） | 完全無影響 |
| 日後維護者理解成本 | 高 | 低 |
| 工時 | 約 11 人日 | 約 12 人日 |

**建議**：如果 DDL 申請在本案時程內可以完成（Q-B1），採用本方案；如果 DDL 申請流程太長或不被允許，維持 v0.3。
