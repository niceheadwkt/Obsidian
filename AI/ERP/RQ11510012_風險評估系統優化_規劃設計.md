### 3.1 R1：新增風險評估之版次管控（`eajcRE00CRN.doInsert()`）

**規則**：系統日 ≥ 版次管控生效日（系統參數）時，新增前檢查同部門所有風險評估：

```sql
-- 有任一筆回傳即不可新增
SELECT A.FORMNO, W.REPORTID, W.DOCSTATUS
FROM DB.TBEARE00 A
JOIN DB.TBEAWORKDOC W ON W.WORKDOCID = A.FORMNO
WHERE A.COMPID = ? AND A.DEPT = ?            -- 不分 RECode 的 Y/S（年度、偶發一起管控）
  AND NOT (W.REPORTID = '0002' AND W.DOCSTATUS = 'E')
  AND A.FORMNO >= ?                           -- 待確認：歷史資料的排除條件（見 Q1）
```

- 不符合時訊息：「部門 ○○ 尚有【風險與機會評估】未簽核完成或尚未進入機會階段（文號：…），需全部簽核完成才可新增【風險評估】」。
- 不檢查高風險（RE04）簽核狀態。

### 3.3 R3：新版複製（`eajcRE00CRN.doCopyLatest()` 新增）

> 2026-10-08 使用者補充指示：在原【複製】旁增加【新版複製】，依照「最新B表匯出」的 SQL 抓法，並參考【複製】功能的動作；**關聯文件編號（REFNO）要記錄到 `tbeaWorkDocEX`**，以便追蹤新評估編號每一項的原始依據；REFNO 開頭為 **HC-** 者，除了要複製該高風險文號的**高風險改善追蹤異動資料**，也要執行 (EAJJRE20N) 高風險改善追蹤的**【預估評估】**動作。

**做法**：不用 `INSERT … SELECT` 一次寫入，改為「用最新B表 SQL 取出每一列（含 REFNO），再由 Java 逐列處理」，因為每一列要依 REFNO 類型做不同的動作。

#### 3.3.1 共用 SQL 調整（`eajcRERpt`）

把 `exportLatestB()` 的 SQL 抽成 `getLatestBSql(compId, dept)`，讓匯出與新版複製共用。複製用的版本要**多帶出鍵值與文號欄位**（匯出時不輸出這些欄位即可）：

| 加帶欄位 | 來源 | 用途 |
|---|---|---|
| FROMFORMNO | B.FORMNO（LATEST_RA） | 來源評估文號 |
| FLOW0CODE、FLOW1CODE、SRLNO | B.* | 寫入新 RE03 的鍵（不要從 KEYNO 字串拆） |
| REFTYPE | RA／HR／HC／RO | 判斷處理方式 |
| REFDOCNO | HR、HC＝高風險文號；RA、RO＝來源評估文號 | 寫入 WorkDocEX |
| HRVERSDATE | HD／HA 的 VERSDATE | HC 複製異動資料時使用 |

#### 3.3.2 處理步驟（單一交易）

1. **檢核**
   - 目標 formNo 的 vers 必須為空（未確認），沿用 `doCopy()` 的檢核。
   - 操作者必須是目標版的建立者（`doEstimate` 也有同樣限制）。
   - 用 `getLatestBSql()` 取得 LATEST_RA；查無時提示「無已簽核完成之【風險與機會評估】可複製」。
2. **清除目標**：`removeByFormNo` RE01、RE02、RE03（同 `doCopy`）；另外清除本版先前「新版複製」產生的 RE04、RE042、RE043、WorkDocEX（追蹤列與高風險列）、WorkDoc(C3)、Annotate，重複執行時才不會殘留。
3. **複製 RE01、RE02**：沿用 `copyByFormNo(compId, fromFormNo, toFormNo)`。
4. **逐列處理最新B表結果**：

| REFTYPE | RE03（7 欄） | WorkDocEX 追蹤列 | 其他動作 |
|---|---|---|---|
| RA | 來源原值 | 寫入（RA） | — |
| RO | RE13 的 7 欄（D／I） | 寫入（RO） | — |
| HR | 前 3 欄＝RE04、後 4 欄＝RE042 status 30 | 寫入（HR） | — |
| HC | 來源原值（仍為等級 1、2） | 寫入（HC） | **見 3.4：複製異動資料＋執行預估評估** |

5. **不鎖定**：複製後 RE01～03 仍可自行修改。
6. 訊息：「新版複製完成！來源文號 ○○；流程 n、A 表 n、B 表 n 筆（RA n／RO n／HR n／HC n，已產生高風險文號 n 筆）」。

> 注意：`exportLatestB` 用 `dejcQueryDAO`，因為 `zafcDAO` 不接受 `WITH` 開頭的 SQL。

#### 3.3.3 關聯文件編號寫入 `tbeaWorkDocEX`

`tbeaWorkDocEX` 結構：`WorkDocID`（主鍵）＋`field1`～`field7`。現行只用在高風險文號：WorkDocID＝高風險文號，field1～5＝formNo＋flow0＋flow1＋srlNo＋RE04.versDate，field6、field7 空白。

本案新增「追蹤列」。**v0.3：已確認 field7 為 10 碼**，放不下關聯文件編號（高風險文號 28～31 碼、評估文號 18 碼），改用下列配置，不改表結構：

| 欄位（寬度） | 內容 | 範例／說明 |
|---|---|---|
| WorkDocID（40） | `CP`＋新 formNo＋flow0＋flow1＋srlNo（**4 碼補零**，RE03 srlNo 寬度 4） | 2＋18＋3＋3＋4＝30 碼；新 formNo 包含在這裡 |
| field1（40） | **關聯文件編號**（HR／HC＝舊高風險文號；RA／RO＝來源評估文號） | |
| field2～4 | 新 flow0、flow1、srlNo | 方便與 RE03 對照 |
| field5（10） | **空白** | 現有查詢都以 field5＝versDate 比對，留空就不會被當成高風險列 |
| field6（10） | 關聯類型 RA／HR／HC／RO | `HC` |
| field7（10） | HC 移轉完成時寫入**核准日**（8 碼）；空白＝尚未移轉 | 也是防止重複移轉的旗標；新高風險文號可由新鍵＋此日期用 `queryWorkDocEX()` 反查 |

設計理由與注意事項：
- **為什麼加 `CP` 前綴**：防止 WorkDocEX **主鍵撞號**。高風險文號的 srlNo 不補零（`getWorkDocNumber()`：formNo＋flow0＋flow1＋srlNo＋3 碼流水），若追蹤列不加前綴，追蹤列 srlNo＝1001（`X1001`）會和高風險列 srlNo＝1、流水 001（`X1`＋`001`）相同。（v0.2 寫「避免 getWorkDocNumber 取號解析失敗」有誤：該方法查的是 `TBEAWORKDOC`，追蹤列不寫入該表。）
- **追蹤列不需要流水號**：一列 B 表只有一筆追蹤列；高風險列需要流水號，是因為同一鍵可有多個改善版次。
- 既有程式查 WorkDocEX 時都會一起比對 field5＝versDate（`queryWorkDocEX`、最新B表的 HR_LATEST），field5 留空就不會被當成高風險文號。
- `eajcRE20CRN.exWD()` 的 `NOT IN (SELECT field1..int(field4) …)` 沒有比對 field5，但追蹤列的 field1 是關聯文號而不是 formNo，**不會**誤排除，v0.2 的「exWD 加 `field6=''`」已不需要。
- 追蹤查詢：`SELECT field6, field1, field7 FROM db.tbeaWorkDocEX WHERE WorkDocID LIKE 'CP' || ? || '%'`（? ＝新 formNo）。
- 可在 B 表畫面（`eajjRE03MainN.jsp`）每一列顯示「原始依據」（RA-／HR-／HC-／RO-＋文號），讓評估者知道資料來源；方案 B 下 HC 列加註「核准後移轉」（Q10、B8）。

### 3.4 R4：HC 項目——複製異動資料＋執行【預估評估】

**HC 的定義**（沿用最新B表）：原等級 1、2，有高風險文號，但不是「RE04 文號簽核 E 且 RE042 有 status 30 完工評估」。

#### 3.4.1 現行【預估評估】（`eajcRE20CRN.doEstimate()` 第 810 行）的動作

1. 檢核畫面鍵值、RE00 存在、**操作者＝RE00 建立者**。
2. RE04：versDate＝系統日；`dateChkForEstimate()` 檢查日期（**預估完工日不可空白、不可小於今日**；改善版次不可小於目前最新版；預估完工日不可小於目前最新預估完工日）；statusCode＝40；依暴露／機率／嚴重度用 `getRanking()` 算 rank，寫入 RE04。
3. RE042：由 RE04 轉入（`_04to042`），actEDate＝系統日，memo＝「yyyy/mm/dd【預估評估】完成!」，statusCode 40。
4. RE043：複製 RE042 一筆，加上 maintUser、maintTS（異動紀錄）。
5. WorkDocEX：同鍵＋versDate 已有文號就報錯；否則用 `getWorkDocNumber()` 取新高風險文號並寫入。
6. WorkDoc：C3、reportID 0001、docStatus F（發文者暫存），標題「文號-部門-高風險追蹤改善作業」。
7. `eaUt.addAnnotate(WD_vo, Ann_vo)` 新增簽核紀錄（Ann_vo 由畫面 v5 帶入）。

#### 3.4.2 HC 列的處理（v0.3 採方案 B：延到風險評估核准時才執行）

v0.2 原設計在新版複製當下就執行預估評估，但新 formNo 此時是 `0001/F`，**違反「第一階段（風險評估維護）須簽核完成才可執行預估評估」**（`isCanExecuteHrisk()` 第 1341 行），且會遇到 C4（確認時狀態被重設為 10，所有按鈕消失）與「複製後改等級留下孤兒高風險文件」的問題。v0.3 改為分兩段：

**第一段：新版複製時（`doCopyLatest()`）**
- RE03 寫入來源原值，WorkDocEX 寫入追蹤列（field6＝`HC`、field1＝舊高風險文號、field7 空白）。
- **不**寫 RE04／RE042／RE043，**不**取高風險文號。

**第二段：風險評估第一階段最後一關核准時（`eajcRE00CRN.agree()`，`WD_vo2` 變成 `E` 的同一交易）**
1. 掃描本單 `field6='HC'` 且 field7 空白的追蹤列。
2. 逐列檢核（全部檢核完才寫入；有問題的列跳過並記錄，**不拋例外擋住核准**，B4）：
   - 新 RE03 仍存在，且 rank 仍為 1、2（空窗期被改掉的跳過，B9）。
   - **重新讀取來源最新狀態**（不用複製當下的快照）：來源若已「完工且簽核完成」就跳過（B1）。
   - 預估完工日過期依 Q11 處理（B5）。
3. **複製異動資料**：來源（舊 formNo＋鍵＋最新 versDate）的 RE043 複製到新 formNo，versDate 改成**核准日**（C1、B12）；來源 RE043 沒有資料時，比照 `eajcRE20CRN.query()` 第 276 行改由 RE042 轉成。**不含簽核資料**（Annotate 不複製）。
4. **執行預估評估**：以來源最新 RE04 的改善措施、暴露／機率／嚴重度、預估完工日，呼叫共用 `estimate()`（3.4.1 第 2～7 步），產生新高風險文號（C3、docStatus F）。
5. **移轉註記**：新 RE042／RE043 的 memo 寫「yyyy/mm/dd【預估評估】完成!（由高風險文號 ○○ 移轉）」；追蹤列 field7 寫入核准日。
6. 核准訊息列出「高風險移轉成功 n 筆、跳過 n 筆（原因）」，並發 DW 待辦訊息給 `re00.createId`（B7）。

第一階段核准只有 `eajcRE00CRN.agree()` 一個入口（`eajcRE10CRN.agree()` 是 0002 階段）。`0001/E` 只會維持到使用者進【風險與機會評估】修改為止（`eajcRE13CRN.update()` 會改成 `0002/F`），所以必須在核准的同一交易中執行，不可留給排程補做。

#### 3.4.3 程式結構建議

把 `doEstimate()` 第 2～7 步抽成共用方法，例如 `estimate(Connection conn, eajcRE00VO re00, eajcRE04VO re04, eajcAnnotate_vo ann, String memoSuffix)`，放在 `eajcRE20CRN` 或新的 bp 類別 `eajcREHRiskBP`。`doEstimate()` 和 `eajcRE00CRN.agree()` 都呼叫它，避免兩份邏輯不一致。

- 取號改用修正後的取號方式（見 3.4.6）。

#### 3.4.6 既有 bug：`getWorkDocNumber()` 跨序號取號

`No＝formNo＋flow0＋flow1＋srlNo`（srlNo 不補零），以 `WORKDOCID LIKE 'No%' ORDER BY WORKDOCID DESC` 取最大號：
- srlNo＝1 的 `LIKE 'X1%'` 也會比對到 srlNo＝12 的 `X12001`；`replaceAll("X1","")` 得 `2001`，加 1 後產生 `X12002`，日後 srlNo＝12 要取 002 時就撞號。
- `catch (Exception)` 一律回傳 `001`，把錯誤吃掉，最後變成主鍵重複。
- 同一張單同時有 srlNo＝1 與 10～19（或 100 以上）的高風險項目就可能發生；方案 B 在核准時一次替多筆 HC 取號，機率更高。

修正建議（**不改**現有文號格式）：改從 `TBEAWORKDOCEX` 取號——`field1～4＝鍵`、`field5<>''`、`WorkDocID NOT LIKE 'CP%'`，取最大號後用固定長度 `substr` 取最後 3 碼加 1。正式機需先查是否已有跨序號的錯號（Q15）。

#### 3.4.7 正式機資料檢查結果（2026-10-09）

1. **跨序號錯號**：`TBEAWORKDOCEX` 高風險列 2,031 筆，WorkDocID 全部等於「自己的鍵＋3 碼數字」；同單同作業下序號互為前綴（如 1 與 12）且都有高風險文號的組合 0 組。3.4.6 的 bug 尚未被觸發，仍建議修正。
2. **flow1Code 帶尾端空白**：部分資料 flow1Code 為 `03 `、`20 `，文號中間會有空格（例：`22Y01MPM42203908214003 3001`）。新版複製組 CP 追蹤列、取號、比對時**不可對 flow 代碼 trim**。
3. **同鍵＋同改善版次有多個高風險文號**：共 397 組，分布 2017～2026/03，**2026/04 起 0 組**（4～9 月新建 16 筆，16 個鍵＋版次各一筆）。即 `eajcWorkDocEX_dao.queryWorkDocEX()` 註解所說的「優化前資料」；例：`26Y01MPM4260120932` 40-`03 `-3 版次 20260112 有 3001（F）、3002（F）、3003（E），RE04 只有一筆。
   - 對方案 B 的影響：HC 的「舊高風險文號」要定義為**該鍵最新改善版次中 WorkDocID 最大者**（同 `queryWorkDocEX()` 的 `order by workdocid desc`）；同版次中較早、停在 F 的文號是廢棄草稿，不列入移轉與 B2 鎖定的判斷。
   - 已確認最新B表 SQL 的 `HR_LATEST` 以 `ORDER BY VERSDATE DESC, WORKDOCID DESC` 取第一筆，即最大號，與上述定義一致。

### 3.5 R5：風險與機會評估不可輸入高風險（`eajcRE13CRN.update()`、`eajjRE13MainN.jsp`）

## 9. 附錄：新版複製 RE03 SQL 初稿（未在 DB 執行過）

> v0.2 註：新版複製已改為「最新B表 SQL 取出每一列＋Java 逐列處理」（見 3.3.1），本節 INSERT … SELECT 只保留作為覆蓋邏輯參考與驗證比對用。

參數：`:compId`、`:fromFormNo`（LATEST_RA 查出的文號）、`:toFormNo`（新版文號）。
RE03 欄位順序依 `eajcRE03DAO.copyByFormNo()`：COMPID, FORMNO, FLOW0CODE, FLOW1CODE, SRLNO, PROCEDURE, REASON, EFFECT, ACCIDENTTYPE, CONSTRUCTCTRL, MANAGECTRL, EQUIPMENTCTRL, EXPOSE, FREQUENCE, SEVERITY, RANK。
與最新B表差異：不需要 RE01／RE02 的 join（只匯出才要 FLOWNAME／WORKSTUS），也不需要 ROW_NUMBER 收斂 RE02。

```sql
INSERT INTO DB.TBEARE03
WITH HR_LATEST AS (
  SELECT X.* FROM (
    SELECT H.COMPID, H.FORMNO, H.FLOW0CODE, H.FLOW1CODE, H.SRLNO, H.VERSDATE,
           H.CONSTRUCTCTRL, H.MANAGECTRL, H.EQUIPMENTCTRL,
           EX.WORKDOCID AS HRDOCNO, HW.DOCSTATUS AS HRDOCSTATUS,
           ROW_NUMBER() OVER (PARTITION BY H.COMPID,H.FORMNO,H.FLOW0CODE,H.FLOW1CODE,H.SRLNO
                              ORDER BY H.VERSDATE DESC, EX.WORKDOCID DESC) AS SN
    FROM DB.TBEARE04 H
    LEFT JOIN (SELECT FIELD1,FIELD2,FIELD3,FIELD4,FIELD5,MAX(WORKDOCID) AS WORKDOCID
               FROM DB.TBEAWORKDOCEX GROUP BY FIELD1,FIELD2,FIELD3,FIELD4,FIELD5) EX
      ON EX.FIELD1=H.FORMNO AND EX.FIELD2=H.FLOW0CODE AND EX.FIELD3=H.FLOW1CODE
     AND EX.FIELD4=H.SRLNO AND EX.FIELD5=H.VERSDATE      -- TODO: FIELD4 型別（exWD 用 int(field4)）
    LEFT JOIN DB.TBEAWORKDOC HW ON HW.WORKDOCID = EX.WORKDOCID
    WHERE H.COMPID = :compId AND H.FORMNO = :fromFormNo
  ) X WHERE X.SN = 1
),
HR_DONE AS (
  SELECT H.*, E.EXPOSE AS E_EXPOSE, E.FREQUENCE AS E_FREQUENCE,
         E.SEVERITY AS E_SEVERITY, E.RANK AS E_RANK
  FROM HR_LATEST H
  JOIN (SELECT Y.* FROM (
          SELECT E.*, ROW_NUMBER() OVER (
                   PARTITION BY E.COMPID,E.FORMNO,E.FLOW0CODE,E.FLOW1CODE,E.SRLNO,E.VERSDATE
                   ORDER BY E.EXPWDATE DESC, E.ACTEDATE DESC) AS SN
          FROM DB.TBEARE042 E
          WHERE E.COMPID = :compId AND E.FORMNO = :fromFormNo AND E.STATUSCODE = '30'
        ) Y WHERE Y.SN = 1) E
    ON E.COMPID=H.COMPID AND E.FORMNO=H.FORMNO AND E.FLOW0CODE=H.FLOW0CODE
   AND E.FLOW1CODE=H.FLOW1CODE AND E.SRLNO=H.SRLNO AND E.VERSDATE=H.VERSDATE
  WHERE H.HRDOCSTATUS = 'E'
),
RO AS (
  SELECT X.* FROM (
    SELECT O.*, ROW_NUMBER() OVER (PARTITION BY O.COMPID,O.FORMNO,O.FLOW0CODE,O.FLOW1CODE,O.SRLNO
                                   ORDER BY O.FORMNO) AS SN
    FROM DB.TBEARE13 O
    WHERE O.COMPID = :compId AND O.FORMNO = :fromFormNo AND O.IMETHOD IN ('D','I')
  ) X WHERE X.SN = 1
)
SELECT B.COMPID, :toFormNo, B.FLOW0CODE, B.FLOW1CODE, B.SRLNO,
       B.PROCEDURE, B.REASON, B.EFFECT, B.ACCIDENTTYPE,
       COALESCE(HD.CONSTRUCTCTRL, CASE WHEN B.RANK NOT IN ('1','2') THEN O.CONSTRUCTCTRL END, B.CONSTRUCTCTRL),
       COALESCE(HD.MANAGECTRL,    CASE WHEN B.RANK NOT IN ('1','2') THEN O.MANAGECTRL    END, B.MANAGECTRL),
       COALESCE(HD.EQUIPMENTCTRL, CASE WHEN B.RANK NOT IN ('1','2') THEN O.EQUIPMENTCTRL END, B.EQUIPMENTCTRL),
       COALESCE(HD.E_EXPOSE,      CASE WHEN B.RANK NOT IN ('1','2') THEN O.EXPOSE        END, B.EXPOSE),
       COALESCE(HD.E_FREQUENCE,   CASE WHEN B.RANK NOT IN ('1','2') THEN O.FREQUENCE     END, B.FREQUENCE),
       COALESCE(HD.E_SEVERITY,    CASE WHEN B.RANK NOT IN ('1','2') THEN O.SEVERITY      END, B.SEVERITY),
       COALESCE(HD.E_RANK,        CASE WHEN B.RANK NOT IN ('1','2') THEN O.RANK          END, B.RANK)
FROM DB.TBEARE03 B
LEFT JOIN HR_DONE HD
  ON HD.COMPID=B.COMPID AND HD.FORMNO=B.FORMNO AND HD.FLOW0CODE=B.FLOW0CODE
 AND HD.FLOW1CODE=B.FLOW1CODE AND HD.SRLNO=B.SRLNO AND B.RANK IN ('1','2')
LEFT JOIN RO O
  ON O.COMPID=B.COMPID AND O.FORMNO=B.FORMNO AND O.FLOW0CODE=B.FLOW0CODE
 AND O.FLOW1CODE=B.FLOW1CODE AND B.SRLNO = INTEGER(TRIM(O.SRLNO)) AND B.RANK NOT IN ('1','2')
WHERE B.COMPID = :compId AND B.FORMNO = :fromFormNo
```

待驗證：
- DB2 是否接受 `INSERT INTO … WITH … SELECT`（DB2 LUW 可以；若不行改成 Java 先 `dejcQueryDAO.getDatas()` 撈出再逐筆 create）。
- `B.RANK` 為 NULL 時 `NOT IN ('1','2')` 為 unknown，該列不會套機會覆蓋；最新B表已上線的寫法相同，兩邊結果一致，但需確認業務上是否要 `COALESCE(B.RANK,'')`。
- 高風險覆蓋後的 RANK 是否需依 `eajcRERankDAO.getRanking()` 重新計算（RE042 的 RANK 已是計算值，應可直接用）。
- 驗證方式：在測試機複製後，用最新B表匯出（exportType=L）比對新版 RE03 的 7 欄，應完全相同。
