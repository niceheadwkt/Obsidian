
本文件記錄了團隊在管理兩三個專案時，如何透過 **Git Submodule（子模組）** 機制建立「共通規範」，同時兼顧「個別專案文件辨識度（防呆）」與「Git 平台（GitHub/GitLab）最佳閱讀動線」的最終結論與檔案範例。

---

## 📂 最終建議之檔案結構

為了防止在複製貼上或編輯時弄錯專案，個別專案的詳細說明文件維持**獨立命名**（帶有專案名稱）；而共通規範則獨立在一個 Git 儲存庫（子模組）中管理。



Project_A/ (專案根目錄)  
├── .git/  
├── .gitmodules # Git 子模組設定檔  
├── README.md # 專案首頁（絕對不能改名，引導分流用）  
├── readme_Project_A.md # 專案 A 專屬的詳細規格與說明（防呆命名）  
└── shared-rules/ # 共通規範的 Git 子模組資料夾  
└── team-docs.md # 團隊共通開發與設計規範

## **✍️ 各檔案內容寫法範例**

### **1. 專案根目錄入口：README.md**

這個檔案是 Git 平台的專案首頁，負責提供一目了然的導覽分流。


```
# 歡迎來到 Project A 首頁

本專案已整合團隊共通規範，請依據您的需求查閱對應文件：

* 📄 [本專案詳細規格與說明](./readme_Project_A.md)
* 🌐 [團隊共通開發與設計規範](./shared-rules/team-docs.md)
```

### **2. 個別專案說明：readme_Project_A.md**

存放該專案特有的架構、規格或操作步驟。最上方加上導覽，方便閱讀者切換。


```
# Project A 詳細規格與說明

> 🧭 ****快速導覽****：[🏠 回專案首頁](./README.md) | [🌐 查看團隊共通規範](./shared-rules/team-docs.md)

---

## 📌 專案簡介  
（這裡開始寫專案 A 的特有內容、環境架構、資料庫邏輯等...）

```
### **3. 共通規範子模組：shared-rules/team-docs.md**

此檔案存在於獨立的 Repo 中，被所有專案共用。**底部統一連回各專案的 README.md 首頁**，完美避開死連結與檔名衝突。

```
# 團隊共通開發與設計規範

這裡記錄了所有專案（Project A、B、C）都必須共同遵守的規則。

## 🛠️ 程式碼與命名規範  
* 資料庫欄位一律使用小寫底線（snake*_case）。*  
_* API 回傳格式必須包含 `status`, `data`, `message`。_

_---_

_### 🧭 導覽_  
_* [🏠 返回當前專案入口首頁](../README.md)_

```
## **⚠️ 實務維護注意事項（重要防呆）**

### **1. 關於 team-docs.md 的路徑跳脫**

在共通規範中，要連回專案首頁必須使用 ../README.md。

- ../ 代表從 shared-rules/ 資料夾**跳出來**回到專案根目錄。
- 請勿在共通規範中寫死 ../readme_Project_A.md，否則 Project B 的使用者點擊時會發生 404 錯誤。

### **2. 人類大腦防呆機制**

堅持個別專案說明檔名帶有專案名稱（如 readme_Project_A.md、readme_Project_B.md）。

- **優點**：當你在 VS Code 或 Cursor 同時開啟多個專案時，分頁標籤名稱不同，**絕對不會發生「複製貼上錯專案」而不自知的慘劇**。

### **3. Git 子模組的日常指令小提醒**

- **複製新專案時**：若夥伴 clone 了專案，記得提醒他們執行以下指令才會抓到共通規範：  
```
    Bash  
    git submodule update --init --recursive
```
    
- **更新共通規範時**：當你在中央儲存庫更新了 team-docs.md，各專案只需要在根目錄執行以下指令即可同步最新文件：  
```
    Bash  
    git submodule update --remote
```
