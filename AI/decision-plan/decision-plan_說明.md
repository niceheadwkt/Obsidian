```bash
  "C:/恆逸/decision-plan/tests/shot.png"
```

三個參數依序是 Edge 的路徑、要測的 HTML 檔（`file:///` 網址）、整頁截圖的存檔位置。另外會產生一張 `shot_alt.png`，是切換到替代方案時的畫面。

**檢查項目（共 17 項）**

| 類別 | 檢查內容 |
|---|---|
| 渲染 | 決策卡張數、翻案風險邊框顏色、〔出處〕與【假設】樣式、修改指令 3 個 |
| 切換按鈕 | 預設顯示已選；點擊後顯示替代方案、按鈕文字與 `aria-pressed` 正確、多個替代方案一起顯示；再點一次切回已選 |
| 收合段落 | 機械性工作預設收合、點標題展開、階段分組、項目數自動計算 |

| 其他 | 頁面沒有 JavaScript 錯誤 |

每項結果會印出 `PASS` 或 `FAIL`，全部通過時結束代碼是 0。

**注意**

- 「替代方案數 2 個」「機械性工作 2 項、2 組」「決策卡 1 張」是照佔位符範本的數量寫的。拿來測填好內容的成品（例如 UUU 案的 `決策計畫.html`）時，這幾項會判定失敗，屬於正常現象，其餘項目仍可參考。

## 二、內容架構

### 1. 檔案結構

```
C:/恆逸/decision-plan/
├─ decision-plan/                ← 原始檔（以後改這裡）
│  ├─ SKILL.md                   ← 規則與工作流程
│  └─ assets/
│     └─ template.html           ← 佔位符版型範本
├─ decision-plan.skill           ← 打包檔（zip 格式），用來上傳或分享
├─ decision-plan.skill.bak       ← 舊版（範本內含 UUU 案內容）
├─ tests/
│  └─ cdp_test.mjs               ← 範本按鈕自動測試（不打包進 .skill）
└─ decision-plan_說明.md         ← 本文件
```

### 2. SKILL.md 的組成

| 區段 | 內容 |
|---|---|
| frontmatter | `name`、`description`（說明觸發時機，也寫明不適用的情況） |
| 開頭指令 | 讀到此 skill 後，第一個動作必須讀取 `assets/template.html`，不得詢問使用者是否要上傳範本 |
| 適用／不適用 | 適用：系統重建、技術棧選型、自建／外購／SaaS、地端／雲端、架構比較。不適用：只要摘要、只有一個方案、沒有限制文件 |
| 格式要求（五條） | ① 每件事一張決策卡，標【已選】 ② 每張卡附【替代方案】和可檢驗的回頭條件 ③ 每條理由附〔文件簡稱 §節次〕，沒有依據的標【假設】 ④ 依「最可能被翻案」排序，並標翻案風險 ⑤ 最後列出機械性工作，依階段分組 |
| 限制 | 不重寫提案內容；不提出文件裡沒有的新方案；提案宣稱的優點要拿限制文件交叉驗證；沒讀過的文件不拿來當依據 |
| 工作流程 | Step 1 讀限制文件 → Step 2 列出要決定的事 → Step 3 依翻案可能性排序 → Step 4 套用範本，產出 HTML |
| 交付後回報 | 各卡的【已選】與排序，以及會議前最需要確認的 2 到 3 個【假設】 |

### 3. template.html 的組成

範本是「資料驅動」的設計：版面和互動功能都寫好了，產出時只要替換頁首的佔位符，再填入 `<script>` 裡的資料區。

**頁首佔位符**

| 佔位符 | 意思 |
|---|---|
| `{{專案名稱}}` | 出現在 `<title>` 和 H1 |
| `{{公司或單位}}` | H1 前綴 |
| `{{場合…}}` | 例如「本週五決策會議用」 |
| `{{撰寫人}}` | 撰寫人 |
| `{{出處代號對照…}}` | 例如「〔現況〕＝現況與限制.md；〔A〕〔B〕＝方案提案」 |

**資料區（四個陣列）**

```js
cards = [{
  title, risk,         // risk 只能是：最高／高／中高／中／低
  riskNote,            // 為什麼排在這個位置
  pick, why,           // 已選方案、一句話理由
  reasons: [...],      // 每條結尾附〔出處〕或【假設】
  cost,                // 選填：會上必須說明的代價
  alts: [{ name, condLabel, conds: [...], warn /* 選填 */ }]
}]
mech     = [{ stage: "階段名", items: [...] }]   // 機械性工作，項目數自動計算
footnote = "頁尾備註"
cmds     = [{ title, text }] × 3                 // 第一個固定是「最關鍵時程里程碑提前」
```

**內建行為（資料區以外，不要改）**

- 決策卡依翻案風險自動上色，卡號自動編。
- 「看替代方案」按鈕：在【已選】與【替代方案】之間原地切換。
- 機械性工作預設收合，點標題展開。
- 修改指令有一鍵複製按鈕，`file://` 開啟時也能複製（有 fallback）。
- 文字中的〔…〕和【假設…】會自動套用醒目樣式。
- 深色底；字型堆疊包含 `Microsoft JhengHei`、`微軟正黑體`；不連任何外部網址。

## 三、使用方式與提示詞

### 1. 事前準備

在同一個資料夾放好以下文件（Markdown、Word、PDF 都可以）：

- **一份「現況與限制」**：時程與里程碑、法遵／資安條文、預算餘額、人力與技能、既有資產、尚未拍板的需求。
- **兩份以上的方案提案**：每份最好有章節編號，出處才能標到 §節次。

限制寫得越具體（日期、金額、人數、條文），決策卡的理由和回頭條件就越可靠。

### 2. 基本提示詞

```
用 decision-plan，讀這個資料夾的〈現況與限制.md〉和三份方案提案，
幫我產出週五決策會議用的決策計畫，撰寫人是資訊課課長。
```

這段要交代三件事：哪些是限制文件、哪些是提案，用在什麼場合，撰寫人是誰。沒有說的話，Claude 會從文件推斷，或在頁首留下佔位符。

### 3. 依情境調整的提示詞範例

**換一個案子（技術棧選型）**

```
用 decision-plan。〈限制_2027預算與人力.md〉是限制文件，
〈提案_Java重構.md〉〈提案_.NET重構.md〉是兩份方案。
場合是下週二處務會議，撰寫人是 nicehead，專案名稱叫「ERP 報價模組重構」。
```

**自建、外購或 SaaS**

```
用 decision-plan 比較自建、外購套裝、SaaS 三案。
限制文件是〈現況.docx〉，特別注意第四節的個資法遵要求。
會議對象是總經理，翻案風險請從「總經理最在意上線速度」的角度排序。
```

**指定排序觀點**（改變翻案風險的判斷角度）

```
用 decision-plan 產出決策計畫，但翻案風險請以「財務長會推翻」為主要角度排序，
因為這次是預算審查會議。
```

**縮小範圍**（只決定特定事項）

```
用 decision-plan，但只需要做兩張卡：主架構選哪一案、第一版範圍。
其他要決定的事放進機械性工作或頁尾備註。
```

**指定輸出位置與檔名**

```
用 decision-plan 產出，檔名用「決策計畫_報價模組重構.html」，
存到 C:/恆逸/Lab3/ 底下。
```

### 4. 產出後的修改

**用頁面底部的修改指令**

決策計畫頁尾有 3 個修改指令（例如「稽核提前到 4 週後」），按「複製」貼回同一段對話，就會依新前提重排計畫。

**自己下修改指令**

```
主管確定要納入手機報修，請把卡 1 改成已選方案 B，重新排序並更新機械性工作。
```

```
CAL 盤點結果是 55 席，請更新卡 5，並評估是否需要回到卡 2 重新決議。
```

```
新增一份文件〈整合商報價.pdf〉，請讀完後更新卡 3 的理由與回頭條件，
頁尾備註也要拿掉「沒讀過報價」那一句。
```

### 5. 交付後要檢查的事

- 檔案裡沒有殘留 `{{`。
- 每條理由都有〔出處〕或【假設】。
- 回頭條件是可以檢驗的具體條件，不是「若情況改變」這類空話。
- 在瀏覽器打開，確認切換、收合和複製按鈕都能用。
- 看 Claude 回報的 2 到 3 個關鍵【假設】，會前先找相關人員確認。
